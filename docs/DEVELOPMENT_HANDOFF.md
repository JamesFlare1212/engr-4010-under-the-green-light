# 开发交接：规则、状态与验收

## 已实施交接（2026-10-21）

现已建立联机应用。状态机在 `server/engine.ts`，SQLite 与权限投影在 `server/store.ts`，HTTP / WebSocket 在 `server/index.ts`，双语剧本改编在 `shared/content.ts`（1.0.0）。本文原规则和验收行为继续约束实现；原 JSON、Word 与独立流程图保留草案版本。运行、部署和已执行验证见 [README](../README.md)、[实现与协议](ARCHITECTURE.md)、[验证记录](QA.md)。

## 先理解现有文件

当前是材料仓库。`content/scenario.zh-CN.json` 提供稳定ID、路线、DC、NPC、后果和时长；GM剧本保留更完整的叙述与主持提示；玩家包可作为玩家界面的内容依据。流程图HTML用于理解交互分支，其字体和绘图代码属于展示参考。

两份 Word 可以人工修改；`tools/build_documents.py` 是原草案的生成源码，无法读回人工修改。修改前比较当前 Word 与生成稿；重新生成默认输出到 `tmp/generated-documents/`，不要覆盖现稿。

## 建议的场次状态

至少保存以下字段，名称可以在实现时调整：

- `schemaVersion`、`scenarioVersion`、`sessionId`、`mode`、当前阶段。
- 玩家临时名称/ID、主导记录、Co-GM分工。
- 规则配置：可用加成、叠加策略、差额分档、补救上限、优势上限。
- 已公开证据；`access` / `evacuation` / `isolation` 三个准备优势。
- 选中路线或自创路线的描述、已接受的代价与关键假设。
- `emergencyKitsRemaining`，初始2。
- 每个目标的行动、负责人、骰点、加成依据、基础和最终DC、差额、原档、补救后的有效档、是否已花物资、实际后果。
- 人员状态、设施隔离状态、通报原话、负责人、后续动作和复盘。

将原始掷骰与有效结果分开保留。用清晰的行动ID避免双击、恢复或切视图重复消耗物资。GM更正已结算行动时，应先回滚该行动引起的资源变化，再重算或要求确认；不能只改显示值。

## 主流程

开场 → 调查/证据 → NPC协商 → 路线决定 → 三个执行目标逐个结算 → 分项结局 → 复盘。

完整版有三次准备检定；简版跳过准备骰，六名玩家两人一组主导三个执行目标。三次执行的顺序允许 GM 合理调整；同一目标只结算一次。

## 算式

默认草案约定：

```text
selectedBonus = 一个有依据的加成（0、+1工具、+2工程、+3领导力）
reduction = max(preparationReduction, creativeReduction)，范围0..2
effectiveDC = baseDC - reduction
total = d20 + selectedBonus
delta = total - effectiveDC
```

五个档位从低到高是 `consequences → twist → near_miss → success → boon`：

- `delta <= -5`：失败并有后果。
- `-4 <= delta <= -3`：失败但有转机。
- `-2 <= delta <= -1`：接近成功/部分成功。
- `0 <= delta <= 2`：成功。
- `delta >= 3`：成功并获益。

自然1没有额外处罚。输入应限制为D20的1..20。若老师采用不同加成叠加方式，应在场次开始时明确配置并保存；不要在看见结果后偷偷提高DC。

## 准备与应急物资

- 准备DC均为11；成功或成功并获益提供对应执行DC降低2。
- 准备失败仍提供全部关键线索，不再对执行追加罚点；准备阶段不能花应急物资。
- 执行基础DC：通路12、转移12、隔离13。
- 执行未达标后，全组可花1份物资提升一档；每次检定最多一次，资源不能为负。
- 结果最高提升到普通成功；原先成功或获益时不显示可消耗操作。
- 采用提升后的整档后果，替换旧档。路线已接受的代价仍保留。
- 更换主导人或路线不会重置物资；准备优势与创意降难度取较高者。

## 必须保持的叙事行为

- 低骰不删除证据，不阻止后续目标，不迫使角色退出。
- 通路失败通过事先存在的备用通路继续，后续DC不滚雪球增加。
- 人员结果可为12人安全、12人撤离且2人需观察、8人撤离且4人在避难室待援。隔离结果不能把已撤离人员改回伤亡。
- 避难室有独立临时保障；隔离失败不自动取消它。
- 隔离、医疗备用交接、真实报告分别记录。高骰不能把玩家的虚假报告自动改成真实，低骰也不能把诚实表达自动改成欺骗。
- 三条路线的检定数量和基础DC一致；差异来自公开代价。GM可以接受有依据的自创方案。
- 课堂用时提示与故事中的十二分钟分开，允许主持暂停讨论。

## 实现后的关键验收场景

1. 完整版：三位玩家准备，另外三位玩家分别执行；主导提示覆盖六人。
2. 简版：跳过准备骰；仍有两份物资，基础DC不变。
3. 无优势，工程+2、骰10、基础DC12，产生总12和普通成功。
4. 差额+2算普通成功，+3才获益；−2、−3、−5正确落档。
5. 差额−3花一次物资，只从转机提升到部分成功；不能连续花第二份达到成功。
6. 已成功的行动无法浪费物资；刷新、双击、导入场次不会重复扣除。
7. 准备优势2与创意优势2同时存在时，只降低2。
8. 三次低骰仍能结算三个目标，保留备用救援和后续任务。
9. 转移已成功而隔离失败：保持已撤离人数，追加设施与供电待办。
10. 存档往返后保留规则版本、行动ID、原档/有效档、资源和报告；对不支持的版本显示可理解的错误。
11. 玩家展示视图隐藏GM真相；键盘可操作，结果状态有文字说明。

这些行为由规则、存档与联机测试覆盖。运行 `bun run check`、`bun test tests` 和 `bun run build`，或执行 `bun run verify`。人工浏览器与环境验证边界记录在 `docs/QA.md`。

## 文档与来源维护

原件文件名已规范化；真实标题、材料属性及SHA-256保存在 `materials/catalog.json`。`tools/extract_materials.py` 对照目录提取DOCX/PPTX/PDF，遇到校验不符即停止；它只写派生文本。

以后修改内容时更新JSON与相关剧本/玩家材料，并在 `docs/DECISIONS.md` 记录新决定。发布应用时，从结构化内容选择可展示素材；原始课程PDF、组内文档和内部主持笔记需要单独判断公开范围。
