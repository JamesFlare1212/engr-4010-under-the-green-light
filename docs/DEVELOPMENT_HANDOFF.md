# 开发交接：规则、状态与验收

线上游戏使用 Bun、Svelte 5、Vite 8、TypeScript、SQLite 和 Tailwind CSS 4。运行与检查从 [README](../README.zh-CN.md) 开始；依赖版本与升级检查见 [依赖与工具链](DEPENDENCIES.md)，网络协议见 [实现与协议](ARCHITECTURE.md)，剧情资料入口见 [剧情与世界](SCENARIO.md)。跨状态不变量、已修复竞态、草稿/恢复约束及测试边界见 [隐式状态机审查](STATE_MACHINE_AUDIT.md)。

## 状态转换与推进条件

`lobby → briefing → investigation → negotiation → route_choice → execution → ending → debrief`

1. 房主分配 1–4 个 GM 席位；至少一名玩家参与才能开始。模式和骰子设置在开始后固定。
2. 调查公开全部关键证据。完整版完成三项准备检定；精简版跳过准备，保留执行基础 DC 与两份物资。
3. 协商、路线和补救均由 GM 手动结束投票；结束前可改票，任何人都看不到他人选择。平票由 GM 记录理由裁决；空投票不产生决定。
4. 路线确定后进入执行。GM 公布行动、备用方案和 DC；玩家申请主导或协助，系统从申请者中等概率抽选一位。主导记录只提示轮换，不改变概率。
5. 检定为 `recruiting → selected → resolved`。重新招募保留行动与 DC，但更换检定 ID，使旧轮次延迟申请与骰点失效。虚拟骰仅由抽中的玩家触发，服务端生成点数；实体骰由 GM 录入 1–20 的整数。
6. 同一执行目标只结算一次，三个目标可以重排。低骰且尚有物资时自动发起补救投票，处理完后继续下一目标。
7. 三项目标完成后共同编辑交接。所有成员可生成草稿、保存未完成内容；实际通报、具名负责人和更新时间齐全后，GM 才能进入复盘。

GM 可以自创路线、调整叙事和人员 / 设施实际结果。自创路线更改后重新投票；玩家应在接受路线前看见代价与假设。

## 检定算式

```text
selectedBonus = 0、+1 工具、+2 工程或 +3 领导力，选一个
reduction = max(preparationReduction, creativeReduction)，范围 0..2
effectiveDC = baseDC - reduction
total = d20 + selectedBonus
delta = total - effectiveDC
```

加成与创意依据说明为选填。准备 DC 为 11，成功或获益提供对应执行 DC 降 2。执行基础 DC：通路 12、转移 12、隔离 13。自然 1 按普通差额结算。

| 差额 | 档位 |
| --- | --- |
| `delta <= -5` | `consequences`：失败并有后果 |
| `-4..-3` | `twist`：失败但有转机 |
| `-2..-1` | `near_miss`：部分成功 |
| `0..2` | `success`：成功 |
| `>= 3` | `boon`：成功并获益 |

准备失败仍给出全部关键证据，不追加执行罚点。每次失败执行最多用一份应急物资提升一档，最高普通成功；成功、获益和准备检定不能消耗物资。提升采用新档完整后果，路线已接受的代价仍保留。

## 状态与持久化约束

- 原始骰点、基础档与补救后的有效档分开记录。幂等命令 ID 与状态在同一 SQLite 事务保存，重试不能重复扣物资。
- GM 更正当前阶段最后一次已结算骰点时，先退回该次物资，再按原 DC 重算并记录理由。仍失败、有物资且有玩家时自动发起全新补救投票，不复用旧票；历史空票或保留票不永久封锁当前补救。更早的行动保持历史，通过公开叙事记录后续调整。
- 投票保留最近 300 轮、日志最近 1500 条；运行时和导入的数量边界一致。导入还检查阶段前置条件、招募主导及准备优势来源，不能仅靠存档自身算式自证。
- 人工结果覆盖是全量且持续优先的快照，后续检定不会自动刷新其中任何分项，当前没有清除覆盖命令。外部命令的失败原子性来自 `Store.command()` 事务，而不是裸 `execute()`。
- GM 写操作检查版本；并发冲突返回最新投影。玩家申请与投票绑定对应 ID，可以并发提交。
- 人员、隔离、医疗交接和实际通报分别记录。低骰不删除证据或阻断后续目标；隔离失败不撤销已完成的人员转移，也不取消避难室保障。
- 事实与未知由成员实际表达决定。高骰不把虚假通报改成真实，低骰不把诚实表达改成欺骗；不生成伦理总分或课程成绩。
- 客户端只接收权限投影。非 GM 不接收私密上下文和笔记；降权或进入展示模式清理本地私密笔记弹窗与草稿。断线时只读，恢复后采用服务端快照。
- 连接代际与提交生命周期分别保护异步回调；通用 HTTP 解析不能绕过检查应用快照。同版本 HTTP 不覆盖实时在线名单，HTTP 补取不解锁写入。expired 不被浏览器联网/前台事件自动解除。
- 表单必须带草稿起始版本，不能用最新房间 revision 给旧草稿“补票”。`room-drafts.ts` 的仓库跨页签/章节保留输入与原 revision，成功只确认提交版本，不清后来的输入；较早章节草稿可查看/导出。实体骰/叙述/更正按 check ID，准备/执行计划分开。确认离开或刷新后不承诺恢复未提交的内存草稿，不能把它当成服务端自动保存。
- 导出 `green-light-save` v2，接受 v1/v2；Room schema 仍为 1，SQLite user_version 升级为 2，兼容读取旧库并阻止旧程序降级写入。恢复新房间建立新房主，实际历史身份进入不含 role 的 `archivedMembers`，不占 40 个 active 席位、不继承旧令牌。姓名显示可查历史，授权和新投票/招募不得查历史身份。
- 存档文件预算 32 MiB UTF-8 字节，导入包裹另有 1 KiB 余量；普通 POST 仍为 1 MiB。持久化前同时检查当前及最坏恢复后的漂亮 JSON，超限以 413 原子拒绝、不占去重 ID。恢复上下文替换而非追加；未执行过命令/没有历史引用的恢复专用房主席位不反复积累，实际参与后的身份始终保留。

## 关键验收

1. 完整与精简模式可从开场走到复盘，全部低骰仍有可继续的救援、封锁和后续安排。
2. 差额 `+2/+3/-2/-3/-5` 正确落档，准备与创意都为 2 时仍只降 2。
3. 差额 −3 花一份物资只从转机升到部分成功；重复请求不能再扣物资。
4. 人员已撤离而隔离失败时，保留人数并追加设施和供电待办。
5. 全员投票后仍可改票，只有 GM 关票后公开计票；平票、空票和双 GM 竞争正确处理。
6. 玩家不能执行 GM 操作或获取私密内容；只有选中的玩家能触发虚拟骰。
7. 未完成交接可保存；过期编辑不能覆盖新版本；报告完整后才能进入复盘。
8. 刷新、重连、SQLite 重启与存档导入保留进度，权限、资源和状态保持一致。还应覆盖旧连接/旧招募/旧文件读取晚到，以及提交中继续编辑，而不只测顺序通关。

原跨页草稿、满员恢复容量与大存档上限错配已修复，复现/回归及明确容量边界见 [审查记录 R1–R3](STATE_MACHINE_AUDIT.md)。验收还包括满员 v1 文件恢复后加入新团队、临近完整字节预算时连续导入/导出，以及恢复元数据不能挤占预留。

执行 `bun run check`、`bun test tests`、`bun run build`。验证范围及平台限制记录在 [QA](QA.md)。修改剧情时同时核对双语文本、私密真相、剧本参考和内容回归测试；修改存档结构时显式处理版本兼容。
