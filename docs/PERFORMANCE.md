# 多人同步性能调查

2026-11-04，Windows x64 / Bun 1.4.4；调查对象是投票、申请和推进后其他设备更新慢。已确认广播放大与客户端重复处理；文件 SQLite 的同步事务成本也明显，不能仅凭流量下降推定响应时间同比下降。

本页数据是 2026-11-04 的历史测量，不包含后续状态/恢复修复增加的存档字节预算与草稿逻辑。合并后的功能验证及小规模压测冒烟见 [QA](QA.md)，不能直接将本页数字当成当前版本性能。

## 已确认的问题与改动

- 原实现每条命令都立即向所有连接发送完整状态。12 人房间内 11 人同时投票，每轮生成 132 份快照；历史记录、已结束投票、行动与报告都重复传输。连接认证与关闭也会广播，集中加入时同样放大。现在使用每房间固定 16 ms 窗口合并广播，只发最新完整投影。同一身份的多个标签页复用已序列化消息。
- 操作者同时接收 HTTP 响应与 WebSocket 的相同状态；原客户端两次更新 Svelte store，并两次同步序列化、写入 localStorage。现在跳过相同房间、身份、版本与在线名单的快照，保留同版本的在线变化；阅读缓存延后 250 ms 合并写入，后台、离页和断开连接时刷新。服务端事务、权限投影、幂等与规则保持原行为。
- 本机文件 SQLite 仍在主线程同步提交；历史增加也会扩大每条命令整份状态的读写。没有降低 SQLite 的持久化级别。服务端仍发送完整投影与完整 HTTP 响应，长历史或慢连接的单份状态成本仍在。

## 复现

```bash
bun run benchmark:sync 12 300 5 file
bun run benchmark:sync 12 300 5 memory
bun run benchmark:sync 40 1500 5 file
```

参数依次为总人数、历史记录条数、并发投票轮数、存储方式。默认值为 `12 300 5 file`。脚本在回环地址启动临时服务，创建独立数据库，连接每位成员，等全体在线后计量；每轮所有玩家同时投票，等所有连接收到最终版本再开始下一轮。结束清理连接与临时数据库，不读写实际游戏数据。`memory` 用来辅助区分文件存储成本，不代表生产部署。

输出的 `snapshots` 与 `websocketMiB` 仅计投票期间 WebSocket 的 state 消息数量与未压缩 UTF-8 负载，不含建立连接阶段、HTTP 响应或协议开销。`storeCommandTotalMs` 是全部命令的 Store 执行累计耗时，包含状态机与事务提交；`commandP*Ms` 是请求发起到 HTTP 响应体接收完成的分位数；`allPeersSyncP*Ms` 是一轮请求发起到所有 WebSocket 客户端收到最终版本的分位数。5 轮中的 P95 为其中最慢一轮，不是长期尾延迟估计。

## 同机对照记录

基线取自 `e93678f` 的 `server/index.ts`，使用相同脚本和相同 Store / 状态机；修复版使用广播合并。以下为一次配对运行，12 人、300 条历史、5 轮共 55 条命令：

| 存储 | 实现 | 快照数 | WebSocket MiB | Store 累计 ms | 全体同步 P50 / P95 ms |
| --- | --- | ---: | ---: | ---: | ---: |
| 文件 SQLite | 基线 | 660 | 60.71 | 1482.01 | 410.51 / 814.86 |
| 文件 SQLite | 修复 | 60 | 5.52 | 1289.39 | 512.93 / 812.46 |
| 内存 SQLite | 基线 | 660 | 60.71 | 89.79 | 160.47 / 884.39 |
| 内存 SQLite | 修复 | 120 | 11.04 | 79.26 | 208.91 / 368.52 |

该次文件存储对照中快照与 WebSocket 流量下降约 91%，同步 P95 基本持平，P50 有波动，不能宣称总体延迟已同比改善。合并批次数受请求到达时间、磁盘耗时与事件循环调度影响；其他修复版文件存储运行发出了 72 份快照。

40 人、1500 条历史的基线在等待全体在线时 15 秒超时（最后观测在线 35 人），未进入有效计量阶段。修复版的文件 SQLite 测量完成了 195 条投票：200 份快照、90.22 MiB，全体同步 P50 911.35 ms、P95 1908.39 ms。内存 SQLite 同配置也完成了 195 条命令。超时证明该压力下原广播链路未完成同步，但未单独确认连接丢失的底层原因。

## 验证与适用范围

回归覆盖一批 20 条命令全部持久化、仅广播最终状态、个人投票投影、GM 私密内容、房间独立调度、停服清理、同版本在线变化和缓存合并。完整检查见 [QA](QA.md)。

基准客户端与服务端处于同一 Bun 进程，包含回环网络与客户端 JSON 解析成本；不模拟真实浏览器的渲染、localStorage、局域网带宽、公网 TLS 代理或后台休眠。缓存改善由行为测试验证，尚未测量真实手机帧耗时。没有访问部署服务器或修改其配置，线上根因仍需结合实际人数、房间历史、部署磁盘与代理确认。

若部署后仍慢，优先在服务器上以相同参数运行文件与内存对照，确认是否由磁盘提交主导；再考虑减少历史快照负载或增量同步。该工作需要继续保留权限过滤、同版本在线更新、断线全量恢复和命令事务约束。
