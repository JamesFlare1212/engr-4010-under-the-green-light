# 隐式状态机：审查、修复与验证边界

本记录针对应用自己维护的状态与异步生命周期，不审计框架内部状态，也不替代完整安全审计。核心问题不是“缺少状态机库”，而是同一业务状态被空值、历史记录、版本号和异步回调分别解释。下面区分已修复缺陷、明确约定与验证边界。原 R1–R3 已落实修复及回归测试；测试通过仍不代表所有状态组合、浏览器和部署环境都已覆盖。

## 审查范围

| 层次 | 检查的状态与转换 |
| --- | --- |
| 规则 | 阶段推进、规则冻结、目标唯一性、准备优势、招募/主导/骰子授权、名单变化、投票/平票/空票、路线确认失效、补救/更正、证据公开、人工结果、交接完整性、反思与计时 |
| 存储/协议 | 命令去重、版本冲突、失败回滚、权限投影、存档恢复、历史容量、客户端身份切换、快照次序、连接代际、重试/心跳/降级、认证终态、在线身份去重 |
| 界面 | 创建/导入向导、组件卸载与草稿、协作编辑、展示模式/降权、朗读、二维码、复制、骰子动画、通知、浏览器语言 |
| 外围 | dialog/details、Blob URL、服务停止及开发子进程回收 |

`Room.phase`、`Check.status`、`Poll.status`、`connection`、`copyStatus` 本身已有显式取值，但不能单独回答“现在能做什么”。例如 `closed + tied + !outcome` 仍是未完成投票；`resolved` 检定仍可能等待补救，且可能允许更正。

## 必须保持的实现约束

### 规则与权限

- `isPendingPoll`、`canOpenKitVote`、`handoverComplete` 在 `shared/state.ts`；界面和服务端使用同一纯判断，服务端始终独立校验权限和输入。不要在前端导入 server 模块。
- 检定 ID 同时是**当前招募轮次的授权边界**。重新招募会更换 ID；稳定的是剧情 objective ID，不是未结算招募 ID。已处理旧命令的幂等重放只返回状态，不重做回应。
- `resolved` 不等于结果永远不变。更正会退款并重置有效档；新补救投票不能沿用旧票，且同一当前结果最多消费一份物资。
- 补救入口仅面向当前最后一项已结算执行检定。开始后续检定或离开执行阶段后，不能回头给早期行动消费物资。
- 投票名单缩减仍不自动关票；招募名单缩减可能使抽选条件成立。这两种自动转换不能混用。
- 人工 `override` 是**全量、持续优先的结果快照**，覆盖人员、隔离和医疗三项。后续骰点、更正和补救都不会覆盖它；当前没有清除覆盖的命令。不要将其理解为只修改一个数字的临时补丁。是否改成分项覆盖/增加清除操作需要另行决定。
- `report.truthfulness` 属于人工判断，不随骰点或人数变化自动改写；交接可保存不完整草稿。进入 debrief 的完整性是入口条件，不应误当成 debrief 内报告永远不能再修改。

### 事务与恢复

- 外部写操作必须经 `Store.command()`。`execute()` 会直接修改传入对象，部分分支在之后的检查失败前已经改了内存；**不能把裸 execute 的失败当成回滚**。
- `Store.command()` 每次读取独立状态，状态更新、revision 和去重记录同事务提交。失败命令不得占用去重 ID。`tests/store.test.ts` 专门验证“先使旧路线失效、再因无玩家创建新投票失败”的回滚。
- 玩家并发不等于允许过期授权：vote 绑定当前 poll ID，volunteer/roll 绑定当前招募 ID；校验 revision 无法替代这些目标与轮次检查。
- 存档导入既要验证字段，也要验证字段之间的来源关系。但当前验证不是对所有事件历史的形式化可达性证明。
- 当前导出 `green-light-save` v2，读 v1/v2；Room `schemaVersion` 仍为 1，SQLite `user_version` 升级为 2，拒绝旧程序降级写入。旧库兼容升级、旧 JSON 补 `archivedMembers=[]`，不改变已有令牌。恢复新房间则建立新房主和新令牌，历史身份无 role、无席位，只用于署名。
- `shared/members.ts` 的姓名查询同时查当前与历史身份，只供显示；认证、角色分配、招募与投票只能查 active members。不可将历史查询 helper 用作授权。
- `shared/archive.ts` 统一 UTF-8 字节限制：文件/完整存档 32 MiB，导入请求额外预留 1 KiB 的 `{ name, save }` 包裹，其他 POST 仍为 1 MiB。读取实际字节，也检查无 Content-Length 的流式请求。导入/导出 HTTP 传输超时为 120 秒，其他请求仍为 12 秒。
- 投票保留最近 300 轮、日志最近 1500 条，较早明细不在导出中。检查结果/资源/报告仍是权威记录；不得只靠扫描尚保留的投票推导库存。
- 在线人数由服务端当前认证连接集合按成员去重推导，不写入房间 revision。成员离线不删除席位或既有决定。

### 客户端异步边界

- socket generation 与提交 mutation 是不同生命周期。同身份联网重建连接不应自动丢失正在提交的命令；切换身份或显式恢复会使旧提交失效。
- 通用 HTTP 解析函数不得无条件应用状态、弹出旧身份通知或改变新连接。所有异步副作用都在拥有该生命周期的调用方内执行。
- 同版本不总表示相同在线名单。HTTP、socket、缓存的优先级必须测试，不能仅用 `< revision` 防倒退。
- HTTP 补取只恢复可读快照，不把连接标为 live。断线写入不排队；网络不确定时自动重试使用同一个命令 ID。
- 取消异步工作不一定能取消 I/O；即使 File.text/Clipboard 的工作已经开始，过期结果也不能改变新选择、反馈或焦点。
- 等待提交不意味着用户不能继续输入。成功回调只能确认提交时的草稿版本，不能无条件清空当前输入。

## 原 R1–R3 的修复闭环

### R1 / 已修复：房间级草稿与提交版本

`src/lib/room-drafts.ts` 为每个已挂载房间/身份提供独立仓库，生命周期高于页签和阶段 key。交接、个人资料、自创路线、房间设置、结果调整、检定计划、实体骰、更正、叙述与反思都从同一仓库读取，而非在卸载时拷贝本地旧值。

- 检定计划按 preparation/execution 分开；实体骰和结果表单按实际 check ID 分开。重新招募后的新 ID 不继承旧骰点；旧目标的自创行动不会被自动迁移到新目标。
- 每次输入、取消/重新打开、重新载入和版本复核均维护草稿版本。成功只确认提交时的版本；新输入、编辑后还原原文（ABA）、其他题目/检定的新稿不被旧回调关闭或清空。
- 房间级“本机未提交草稿”面板可查看/导出较早章节的未提交文本，避免阶段变化后虽然保留却无法取回。稿件保留最初 revision，必须明确复核或重新载入，不能自动给旧稿换最新版本。
- 展示模式隐藏 GM 草稿且清理私密笔记，不销毁待提交的 GM 计划；真实降权清除全部 GM 草稿并使旧回调失效。
- 离开房间（含 SPA 返回）有明确丢弃确认，刷新/关闭注册 beforeunload 提示。草稿仅在当前房间页面的内存中，不跨确认离开、刷新、标签页或设备持久化；不把浏览器可能不显示的离页提示当成自动保存保证。

回归证据：`tests/room-drafts.test.ts` 的仓库/版本/隔离测试，`tests/ui-state.test.ts` 的实际 Handover/People/Stage/Debrief/Room 脚本重建与异步回调，`tests/check-drafts.test.ts` 的实际 CheckPanel 脚本及模板函数绑定。

### R2 / 已修复：历史身份不占 active 席位

旧房间 40 人导入后，实际参演身份进入 `archivedMembers`，原姓名、ID、行动、选票、日志与反思保持署名；新的房主是新身份，仍可邀请 39 位新成员并补齐 GM。历史记录不进入新投票/招募，不持有 role 或登录凭证，不能被角色分配命令重新授权。界面的行动、反思、投票、成员和日志展示使用历史姓名查询。

恢复行为使用 `room.recovery` 记录可替换的恢复上下文，不伪装为新的剧情行动或追加恢复日志。仅用于接收存档、从未执行命令且未被任何历史记录引用的 `recoverySeat` 可以在再次恢复时被替换；一旦成功执行任一命令即转为真实参演身份，下一次恢复必须保留，不能借此删掉任何署名工作。反复纯导入不会无意义地积累房主和恢复日志。

回归证据：`tests/archive-recovery.test.ts` 的满员 v1 导入、39 位新成员、旧令牌拒绝、历史署名/记录保留、待完成检定继续、反复 v2 恢复、旧 SQLite JSON 兼容和恢复房主实际参与后保留。

### R3 / 已修复：导出、传输与恢复使用一致字节预算

原先约 1.29 MB 的合法导出会撞上 1 MB 请求上限。现在专用导入支持 32 MiB 文件，普通命令保持 1 MiB；以 UTF-8 实际字节而非 JS 字符数判断。Home、Bun 请求读取、导出格式化和持久化共用限制，出站完整快照背压预算也同步调整；入站 WebSocket 仍限 4 KiB。

`Store.save()` 在提交任何状态前，同时预算当前漂亮 JSON 与**最坏合法房主姓名/时间宽度下的恢复后漂亮 JSON**，给恢复身份和上下文预留空间。纯恢复席位/元数据可替换，使这个界限在再次导入后继续成立，而不是把近上限存档恢复后才发现元数据超额。超预算写入以 `archive_too_large` / 413 明确拒绝，事务回滚、不占命令去重 ID，不删重要历史文本。

回归证据：真实 HTTP 的大于旧 1 MiB 存档往返、Unicode/控制字符转义与包裹开销、Content-Length/流式请求边界、大快照；还有完整预算精确填满时的连续恢复、恢复后导出和超额事务原子性。32 MiB 是明确容量限制，不承诺无限历史；超出预算的旧版或手工存档需在导入前处理，不能因失败创建半成品房间。
